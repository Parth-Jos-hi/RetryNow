# Dataset Guide — Synthetic Failed-Payment Transactions

## Why synthetic?

Real Razorpay transaction data is private and cannot ship with a student project.
So we build a **realistic, deterministic synthetic generator** that:

1. Models the distributions that matter (instrument mix, failure-reason mix,
   transient-vs-permanent recoverability, salary-cycle timing, merchant verticals,
   bank/issuer behavior).
2. Assigns every failed transaction a **latent per-action ground truth** —
   `P(success | action)` for *all* candidate actions (the oracle) — while emitting
   only the **observed outcome of the action the policy actually chose** (selective
   labels, censored outcomes).
3. Simulates **historical policy bias** via a per-reason retry propensity
   (e.g. `server_busy` retried often, `expired_card` almost never).
4. Is seeded → the exact same file can be regenerated by anyone.

> **Honesty rule:** the oracle (latent truths) is used **only** by the evaluator, never
> by the agent. Non-retried payments are never labelled "failure".

## Schema

Generated file: `data/synthetic/failed_payments.csv` (~20,000 rows).

| Column | Type | Meaning |
|---|---|---|
| `txn_id` | str | unique ID |
| `customer_id` | str | masked customer |
| `merchant_id` | str | masked merchant |
| `timestamp` | datetime | when the *failure* happened |
| `amount` | float | ₹ amount (log-normal, ₹50–₹5,00,000) |
| `payment_method` | cat | upi / debit_card / credit_card / netbanking |
| `bank` | cat | bank cluster (bank_a … bank_j) |
| `merchant_vertical` | cat | food_delivery / ecommerce / education_fees / utility_bills / travel / subscription_saas |
| `failure_reason_code` | cat | 11 reasons (below) |
| `customer_instruments` | int | how many instruments on file (1–4) |
| `is_weekend`, `hour_of_day`, `day_of_week`, `day_of_month` | derived | from timestamp |
| `txn_value_bucket` | cat | small / medium / large / huge |
| `risk_score` | float | synthetic risk score (0–1) feeding the mock risk gate — **not** a fraud model |
| `retry_propensity` | float | P(historical policy would have retried) → simulates selection bias |
| `was_retried_historically` | bool | exposure indicator (per propensity) |
| **Oracle (evaluator-only, tagged columns):** `p_success_retry_soon`, `p_success_retry_later`, `p_success_switch`, `p_success_send_link` | float | latent per-action recoverability |
| `retry_success_obs` | int (0/1) | outcome of the action actually taken (may be NaN = never acted on) |

## Failure-reason codes

| Code | Share | Recoverability (seeded) | Driver |
|---|---|---|---|
| `insufficient_funds` | 0.22 | medium ↑ | resolves after salary cycle (1st–5th) |
| `bank_server_timeout` | 0.18 | high | transient; load- and slot-dependent |
| `issuer_decline` | 0.16 | medium | bank risk-decline; often blips |
| `upi_server_busy` | 0.14 | high | peak-time UPI load |
| `network_timeout` | 0.10 | high | transient |
| `otp_expired` | 0.08 | medium | user can re-trigger |
| `card_expired` | 0.05 | low | needs new card |
| `account_blocked` | 0.04 | low | near-permanent |
| `duplicate_payment_block` | 0.03 | medium | resolves after first txn settles |

> `recovery_seed_probs` in `configs/data_config.yaml` seed the *base* addressability;
> the generator adds time-of-day, salary-day, method, amount, and noise effects, and
> derives per-action probabilities so that e.g. `insufficient_funds` recovers much
> better via `retry_later` after the 1st of the month, while `expired_card` has
> near-zero same-card probability and only `switch_method`/`send_link` retain any hope.

## The latent structure (generator-internal causal assumptions)

```
p_success(action) = base(reason) × hour_penalty × salary_day_factor × method_penalty
                    × vertical_penalty × amount_penalty × action_specific_shift
```

`salary_day_factor` spikes `retry_later` success for `insufficient_funds` on the 1st–5th;
`action_specific_shift` encodes that `retry_soon` suits transient reasons, `switch_method`
helps when the instrument is the problem, and nothing helps `card_expired` on the same
card. A predictive model must **learn** these patterns — we never hard-code
reason→action rules into the decision engine.

## Historical policy bias (explicit)

The generator also simulates the *past*: `retry_propensity` is higher for frequently-
retried reasons (`upi_server_busy`, `bank_server_timeout`) and near-zero for
`card_expired` / `account_blocked`. Training on raw history alone would teach a naive
model "not retried = unrecoverable" — which is wrong by construction. The pipeline
therefore works with agent-generated (and any future) logs, keeps propensity columns on
the generated truth, and evaluates propensity-aware. This limitation is documented, not
hidden.

## Derived / engineered features

Produced by `src/features/feature_engineering.py`:

- `amount_log`, `hour_of_day`, `day_of_week`, `is_weekend`
- `days_since_failure_seen_for_instrument` (per (method,bank) lockup proxy)
- `customers_previous_success_rate` / `merchant_previous_success_rate` (rolling,
  strictly-prior rows → leak-free; input row order preserved)
- one-hot encoded categoricals

## Honest limitations

- **All data is synthetic** — distributions are assumptions, not Razorpay statistics.
- **No real behavioral signals** (device fingerprint, velocity) — single-event features.
- **Censored outcomes remain** — "not retried" is counterfactual, not "failure".
- **Annoyance is a proxy** — `customer_friction_score` is a documented simulation
  construct, not measured customer feedback.
- Exact optimal retry timings are **not** known from real data.

## Regenerate

```bash
python scripts/run_pipeline.py --step generate
```

Seeded with `config.yaml → app.random_seed` (42) → reproducible.
